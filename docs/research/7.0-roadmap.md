# FreePDF 7.0: research and priorities

Reviewed 2026-10-30. Recommendation: ship a well-tested, portable MIT PDF and
document-layout core, with convenient document operations and clear diagnostics.
Use the comparison lab as an ongoing release gate. A broad imported feature list
is not a substitute for confidence in everyday documents.

## Upstream and Pdfxport.Net

The official [general](https://docs.pdfsharp.net/General/History.html),
[PDFsharp](https://docs.pdfsharp.net/PDFsharp/History.html), and
[MigraDoc](https://docs.pdfsharp.net/MigraDoc/History.html) histories were reviewed.
Preview 2's enumerated change is licensing activation; the reviewed pages do
not supply an additional functional feature list. Five functional 6.5 requirements
were separately implemented from their symptoms. Do not label this Preview 2
parity or copy its AGPL implementation.

[Pdfxport.Net](https://github.com/gaspardpetit/Pdfxport.Net) is another MIT
continuation of Preview 1. Reviewed HEAD:
`66be2c60174093de2460bee582b3972707c2cfcb`; tree:
`7a0386aa895db1b1b145149b4e9e332362f8b67b`. Its root licence retains empira's
notice and identifies Gaspard Petit's 2026 modifications; licence blob:
`58b47f7344ca2540212a5eb76558f220ac14616a`. Its README describes distinct NuGet
package IDs while retaining API namespaces. Those are sensible compatibility
choices for FreePDF too.

The 76 merged-PR titles inventoried in `pdfxport-prs-2026-10-30.json` identify
useful work around MigraDoc layout, wrapping, borders, fonts and extensibility,
plus named destinations, paths, checksums and reader termination. No source patch
was imported or inspected. A repository-level MIT label does not by itself audit
each patch's origin. Review exact commits and tests before selective reuse;
do not merge another fork's entire current history on that assumption.

## Upstream issue inventory

`pdfsharp-issues-2026-10-30.json` records 91 open issue titles/URLs and local
triage status. Most are **unreproduced backlog**, not accepted defects or promises
to fix all 91. Titles and factual symptoms informed original tests; no upstream
code snippets, attached customer documents or screenshots were copied.

Factual ideas/methods and copyrighted expression are different categories; see
[US Copyright Office Circular 33](https://www.copyright.gov/circs/circ33.pdf).
GitHub content still has its owners' rights under the
[GitHub terms](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service).
FreePDF therefore uses public issue facts for triage but checks licences before
reusing code, prose or assets. This is the project's contribution policy, not a
jurisdiction-specific legal opinion or a staffed clean-room certification.

Implemented here: Core path separation (#396), fully merged tables (#358),
font-cache consistency, signature naming, PNG memory-exhaustion propagation,
tolerant dictionary keys/legacy names, and bounded hex-string parsing. Earlier
zlib/transparency corrections remain. Unit tests and lab evidence are mapped in
`../7.0.0-validation.md`.

The first two priority groups were independently reproduced and corrected on
2026-10-31: stream lengths (#394), hybrid xrefs (#388), cyclic page trees (#361),
trailer loops (#266), inherited MediaBox (#375), multiple content streams (#345),
indexed-PNG transparency (#392), and nested glyphs (#348). Forty-two original
regressions cover those categories; eight lab cases show the resulting behavior.
This does not establish that every attached upstream document now works.

Next investigate ownership and incremental editing: dictionary ownership (#369)
and incremental updates (#302), with explicit preservation/signature semantics.
These remain unreproduced backlog, along with the other unaccepted issue titles.

Issue #415's dependency concern also led to a fresh NuGet audit. The imported
10.0.5 PKCS dependency is affected by Microsoft's October advisories
[CVE-2026-70162](https://github.com/dotnet/announcements/issues/454) and
[CVE-2026-84008](https://github.com/dotnet/announcements/issues/468). Both specify
10.0.13 as the patched 10.x package; this branch uses that version. This does
not certify the entire inherited dependency graph.

## Competitors and useful additions

These are documented vendor capabilities, not independently benchmarked parity.

| Area | Evidence | FreePDF priority |
| --- | --- | --- |
| Friendly document operations | [QuestPDF operations](https://www.questpdf.com/concepts/document-operations.html): page selection, merging, overlays and attachments | Small stream-first merge/split/stamp helpers around existing primitives; preserve links/metadata explicitly and test them. |
| Forms and structured data | [iText features](https://itextpdf.com/products/features): form filling/flattening and XFDF | Start with field enumeration, basic fill/readback and JSON adapters. Flattening needs appearance/rotation/viewer tests; it is not a trivial convenience wrapper. |
| SVG/HTML and text extraction | [iText](https://itextpdf.com/products/features) and [Aspose](https://docs.aspose.com/pdf/net/overview/) cover broad conversion/extraction | Integrate specialized engines where appropriate. A full browser/CSS renderer, shaping engine or OCR system is not an easy core feature. |
| Developer feedback | [QuestPDF feature overview](https://www.questpdf.com/features-overview.html) emphasizes productive authoring/debugging | Fixed-font configuration, missing-glyph diagnostics, document-operation examples and the comparison workbench are achievable differentiators. |

Aspose also now advertises an MIT .NET 8+ library on its
[FOSS product page](https://products.aspose.org/pdf/net/), distinct from its
commercial product. Treat its advertised breadth as a reason to investigate,
not proof of licence provenance, maturity or compatibility. No source audit was
performed in this task.

## Where the industry is moving

PDF is increasingly expected to preserve machine-readable meaning as well as
appearance. The PDF Association's [Well-Tagged PDF work](https://pdfa.org/WTPDF)
and [tagged-PDF projects](https://pdfa.org/tagged-pdf-related-projects/) connect
accessibility with reliable reuse and extraction. Plan a semantic layout model
and validation strategy before promising PDF/UA support; adding a metadata flag
does not make a document accessible.

Hybrid invoices pair a readable PDF with structured XML. The official
[Factur-X project](https://fnfe-mpe.org/factur-x/factur-x_en/) describes its shared
ZUGFeRD/Factur-X approach. FreePDF's new attachment/XMP primitives are useful
building blocks: first provide attachment and metadata helpers, then a narrowly
specified invoice profile checked with independent PDF/A and XML validators.
Do not claim invoice compliance merely because XML is attached.

The recommended sequence is: (1) stable compatibility and reproducible testing,
(2) small document-operation/font-diagnostic APIs, (3) tested hybrid-invoice and
form workflows, and (4) semantic tagging/shaping investments driven by real
requirements. OCR, secure redaction and full HTML/CSS conversion should be
separate integrations until their implementation and validation costs are justified.
