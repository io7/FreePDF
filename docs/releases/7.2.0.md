# FreePDF 7.2.0

FreePDF 7.2.0 removes two more obstacles on the way from PDFsharp 6.2.4: text
works without a font resolver, and `document.Flatten()` works instead of
throwing. Tagged PDF output now keeps a table that runs over several pages as
one table.

## New

- **Text without a font resolver.** PDFsharp 6.2.4's portable build needs an
  `IFontResolver` before it can draw any text, on Windows as on Linux, macOS and
  in containers. With no `GlobalFontSettings.FontResolver` set, FreePDF now uses
  the TrueType fonts installed on the machine. It asks the Windows font table and
  your fallback font resolver first, then folders added with the new
  `GlobalFontSettings.AddFontDirectory`, then the system's font folders.
  - A common family that is not installed is replaced, with a logged warning:
    Arial and Helvetica by Liberation Sans or Arimo, Times New Roman by
    Liberation Serif or Tinos, Courier New by Liberation Mono or Cousine, Calibri
    by Carlito and Cambria by Caladea, which have the same widths; otherwise by a
    DejaVu or Noto font of the same kind.
  - Only fonts FreePDF can embed are used: single-font TrueType files whose
    licence allows embedding. The error names the reason when an installed font
    is not allowed.
  - An application with its own font resolver behaves as before. Set
    `GlobalFontSettings.UseSystemFonts = false` to require one, as 6.2.4 did.
- **Form flattening.** `PdfDocument.Flatten()` draws every visible form field
  into its page as it appears and removes the form; other annotations stay.
  Fields without an up-to-date appearance get one first, and if a value cannot
  be drawn, the call throws before anything changes. In 6.2.4 the method only
  marked the top-level fields read-only, and FreePDF 7.0 and 7.1 threw
  `InvalidOperationException`, so 6.2.4 code that called it compiled and failed
  at run time.
- **Tagged tables across pages.** With `PdfDocumentRenderer.TaggedPdf`, a table
  that runs over several pages is one Table element, and its heading rows
  repeated on later pages are artifacts, so a screen reader meets the table and
  its headers once.

## Fixed

- `GlobalFontSettings.ResetFontManagement()` kept serving typefaces resolved
  before the reset, even after a different font resolver was set.

## Upgrading from 7.1.x

Update all FreePDF packages to 7.2.0 together and rebuild; the assembly version
is now 7.2.0.0. Behaviour changes to check:

- Text that used to fail with "No appropriate font found" because no font
  resolver was set now uses installed fonts. Output then depends on the fonts
  installed; set a font resolver for identical output on every machine.
- `Flatten()` now changes the document instead of throwing. After it, the form's
  values can no longer be read as form data.
- Tagged documents with multi-page tables have one Table element per table
  instead of one per page.

## Validation

All 7.1.1 release gates apply, plus:

- regression tests for the installed-font lookup with original generated fonts,
  form flattening and tagged multi-page tables; 398 regression tests in all;
- a flattened form that renders pixel-identical to the filled form in Poppler
  and MuPDF;
- a three-page tagged table that passes veraPDF's PDF/UA-1 profile and renders
  pixel-identical to the untagged document.

See the support policy (`../support-policy.md`) and the migration guide's
"Fonts" and "Filling forms" sections (`../migrating-to-7.md`).
