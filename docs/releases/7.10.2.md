# FreePDF 7.10.2

FreePDF 7.10.2 fixes how `PdfSignatureVerifier` decides revocation. A signature
with a time-stamp no longer stays Indeterminate because the CRL for its issuing
CA is older than the signature, and `PdfRevocationCheck.Online` asks the issuer
in two cases where it did not. Upgrade if you check signatures, in particular
with `Online`. The public API is unchanged.

## Fixed: a new signature stayed Indeterminate until the CA's next CRL

For a signing time that a time-stamp proves, 7.10 took only revocation data
issued at or after that time. That suits the signer's own certificate, whose
responder answers on request. It does not suit the issuing CA: its status comes
from its issuer's CRL, and a root publishes that a few times a year. Seen with
real files and `Online`: the CRL was issued on 1 October and is valid until
1 May, and a signature made later in October came out Indeterminate with
revocation Unknown, as every new signature would until the next CRL. Signatures
from before 1 October were Valid.

For a CA certificate (any certificate of a chain but its first), revocation
data whose validity window covers the validation time now counts, also when a
time-stamp proves the signing time. It already counted for a signature without
a time-stamp, so a time-stamp made the result worse. The window must also reach
the signing time: a CRL that ran out before the signature was made says nothing
about it, whatever validation time the caller sets. The signer's own
certificate still needs data from after the time-stamp.

## Fixed: Online did not read the CRL after an OCSP answer it could not check

An OCSP answer signed with an algorithm FreePDF does not verify (RSASSA-PSS),
or by a responder certificate it does not accept, says nothing. The
certificate's CRL was asked only when the responder gave no answer at all, so
such a certificate stayed Unknown although its CRL was there to read, and a
revocation in that CRL was not seen. The CRL is now asked whenever the fetched
OCSP answer does not settle the status.

## Fixed: Online did not ask about a time-stamp authority whose DSS data had run out

Data in the DSS that was issued after the time-stamp shows the authority good
at that time, and it went on doing so after it had run out. A key compromise
recorded later voids the authority's tokens (the verifier counts such a
revocation whenever it happened), and only the CA's current answer shows it.
With `Online`, the authority's chain is now asked about when the DSS vouches
for it with data that is no longer current. With data that is still current,
nothing is asked. If the request fails, the DSS's data stands, as with
`Document`.

## Upgrading from 7.10.1

Update all FreePDF packages to 7.10.2 together and rebuild; the assembly
version is now 7.10.2.0. No API change. Behaviour changes to check:

- A signature with a time-stamp whose issuing CA has a current CRL from before
  the signature is now Valid where it was Indeterminate (revocation Good where
  it was Unknown), with `Document` and with `Online`.
- `Online` sends more requests for some files: a CRL download after an OCSP
  answer that does not settle the status, and requests about a time-stamp
  authority when the DSS's data for it has run out.

## Validation

All 7.10.1 release gates apply, plus:

- 1,242 regression tests in all (1,231 in 7.10.1). Each of the three fixes has
  tests that fail on 7.10.1, and the rules that stay each fail a test when
  loosened: the signer's own certificate still needs data from after the
  time-stamp, and nothing is asked while the DSS's data is current.
- The real files that showed the first problem: four files with a signature
  time-stamp, signed under a public CA, checked with `Online` against the CA's
  own responder and CRL. With 7.10.1 three were Valid and one, signed after
  the CA's latest CRL, was Indeterminate with revocation Unknown. With this
  release all four are Valid with revocation Good.
- One independent static review by OpenAI Codex (gpt-6-astra). It found two
  gaps in the first version, both fixed with a test that failed first: a
  validation time set before the time-stamp let a CRL count that had run out
  before the signature was made, and old DSS data kept the CRL from being asked
  when the responder's answer could not be checked.

### Known limits

The limits of 7.10.1 still apply. Changed, or new:

- A revocation of a CA certificate that its issuer records after its latest
  CRL is not seen until the next CRL, as with any CRL.
- An expired time-stamp authority with a current CRL that still lists its
  retirement is asked about once more than needed.
- The size limit for streams other than cross-reference and object streams,
  which the 7.10.1 notes planned for 7.10.2, is not in this release.
