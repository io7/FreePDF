# FreePDF 7.11.0

Release preparation. This version has not been published.

FreePDF 7.11.0 checks existing PDFs for accessibility defects through a native API
and the `freepdf-a11y` command. It also fixes a coordinate-rounding defect and adds
a synthetic corpus with 84,000 producer inputs.

## Accessibility checking

```csharp
using PdfSharp.UniversalAccessibility;

var report = PdfAccessibilityScanner.Scan("document.pdf");
foreach (var finding in report.Findings)
    Console.WriteLine($"{finding.RuleId}: {finding.Message}");
```

The scanner reads the original bytes. It does not repair or save the PDF. Checks
cover document metadata, basic tag structure, text alternatives, page content
associations, embedded font presence and selected annotation relationships.
Each report identifies the checks performed, their outcomes and the document hash.

The result is `Failed`, `NeedsReview` or `Incomplete`. There is no overall
compliance result. `HasFailures` also reports failures found in an incomplete scan.
Coverage is partial PDF/UA-1. Language and description checks establish presence,
not correctness or usefulness. PDF/UA-2, complete Unicode/font validation and all
form/annotation rules remain outside this version's scope. Form XObjects and named
marked-content properties cause incomplete results. So does a damaged file that the
reader had to repair (cross-reference data or stream lengths): the scan then
describes the repaired file. Font embedding is checked for fonts that show visible
text; a font that is only selected, or only used for invisible text (rendering
mode 3), needs no embedded program.

### Command-line tool

The new package is `io7.FreePDF.Accessibility.Tool`. Its command is `freepdf-a11y`.
It requires the .NET 10 runtime. To test candidate packages before publication:

```sh
dotnet tool install io7.FreePDF.Accessibility.Tool --version 7.11.0 \
  --tool-path ./tools --source /path/to/candidate-packages
./tools/freepdf-a11y document.pdf
./tools/freepdf-a11y document.pdf --format html --output audit.html
```

Open `audit.html` in a browser. JSON and SARIF support automated workflows. All
formats retain the partial-coverage status and review requirements. Output paths
must be new files. The tool refuses to overwrite the PDF or an existing report.
Use `--password-env NAME` for encrypted PDFs.

Exit codes are 1 for detected failures (also when the scan is incomplete), 2 for
required human review, 3 for an incomplete scan without detected failures and 64
for command or I/O errors. Only an explicit
`--policy automated` can return 0 when the implemented checks find no failures.
That result still requires further validation and human review.

The early, unpublished tool package used `FreePDF.Accessibility.Tool` as its ID.
The release package uses the `io7.FreePDF*` identity and publishing policy.

## Coordinate precision

Saving page rectangles and real numbers now preserves seven decimal places and
avoids narrowing a `double` to a `float`. A Chromium-generated page previously
changed its page box while retaining its content matrix. That caused a rendering
shift after a FreePDF save. An original regression test covers the defect.
Values from ±1e38 on are still written in single precision, so they stay within
the range PDF readers support. Saved bytes change where a coordinate has more than
three decimals; for example, a new A4 page box is now written as
`[0 0 595.2755906 841.8897638]` instead of `[0 0 595.276 841.89]`.

## Corpus and release checks

The full corpus defines 28,000 distinct parameter sets and generates each with
FreePDF, ReportLab and Chromium. Every PDF receives syntax, page-count, text,
save/reopen and accessibility-regression checks. The full run also compares all
pages of 867 sampled PDFs before and after saving. The sample is chosen by
scenario hash and covers every page geometry and every pair of parameter values.
This is a regression corpus, not 84,000 independently annotated accessibility
verdicts.

The package pipeline builds seven packages. On Linux it installs and runs the CLI
from the package that publication promotes; the Windows job runs the same checks
on a package it builds from the same revision. The checks cover six fixture
outcomes and all report formats. Publication
requires the accessibility workflow as well as the existing core, package and
comparison-lab gates at the exact source revision. It promotes those checked
package files without rebuilding them.

Historical implementation evidence includes a successful 42,000-PDF run and a
3,501-PDF run across the expanded range. The latter includes 1,749 PDFs from the
added scenarios. Those runs precede the release version change. They do not prove
that the complete 84,000-file suite or hosted 7.11.0 release gates have passed.
See `../../eng/corpus/verification-2026-11-16.json` and
`../../eng/corpus/verification-2026-11-16-84k.json` for their exact scope.

## Limits and next work

This release does not establish ADA, WCAG or full PDF/UA compliance. Human review
must assess reading order, meaningful descriptions, table relationships, contrast
and assistive-technology use. Scanner limits bound inspection but are not a
process sandbox. Isolate untrusted PDFs with external time and memory limits.

The next milestone is a complete requirements inventory and optional independent
validation through veraPDF. Native coverage then expands to nested content,
Unicode, forms and annotations. A later review workflow will record human
decisions against the exact PDF hash.
