# FreePDF 7.16.0

FreePDF 7.16.0 checks that the character codes a PDF shows have Unicode
values. PDF/UA-1 requires them (ISO 14289-1 7.21.7): screen readers, search
and copying text depend on them. Both `PdfAccessibilityScanner.Scan` and the
`freepdf-a11y` tool run the check as rule `FPDF-A11Y-UNICODE`.

## What the Unicode check reports

The check reads every code that `Tj`, `TJ`, `'` and `"` show on pages and in
invoked forms, with the active font. Invisible text counts too.

A code fails in these cases:

- A font with Identity-H or Identity-V and an Adobe-Identity descendant shows
  a code that its ToUnicode map does not contain, or the font has no map.
- A simple font shows a code whose `/Differences` name is in neither the Adobe
  Glyph List nor the Zapf Dingbats list, and no ToUnicode entry supplies it.
  Names such as `uni0041`, `f_i` and `A.sc` do not count.
- The ToUnicode value of a shown code contains U+0000, U+FEFF or U+FFFE.

A code passes when a ToUnicode entry maps it, when the font's encoding is named
WinAnsiEncoding, MacRomanEncoding or MacExpertEncoding, when its `/Differences`
name is in one of the two lists, or when an unembedded standard Type 1 font
has it in its built-in encoding.

Each page reports its first missing mapping and its first forbidden value, with
the code, the glyph name where there is one, and the path to the font.

```sh
freepdf-a11y document.pdf --format json --output audit.json
```

## Changed results

- The rule set and the requirements inventory are now version 1.2.0. Matterhorn
  conditions 10-001, 31-027, 31-028 and 31-029 name `FPDF-A11Y-UNICODE` as
  partial native coverage.
- Text in a font that the check cannot assess is `NotChecked`. A scan without
  failures then ends as `Incomplete` and the CLI exits with `3`, where 7.15.0
  exited with `2`. Common causes are TrueType fonts without `/Encoding`, Type 1
  fonts that rely on the built-in encoding of their embedded program, fonts
  with the Adobe-GB1, CNS1, Japan1 or Korea1 character collections, embedded
  encoding CMaps, and ToUnicode maps that the check cannot read. The report
  locates the first such text on each page.
- The scanner reads page content as text extraction does since 7.15.0. A
  string that starts with the bytes FE FF holds character codes, not UTF-16
  text. A number beyond the range of a double ends the scan as `Incomplete` on
  every runtime.

## Known limits

The check does not judge whether a mapped code draws the right glyph, whether
it draws `.notdef` (Matterhorn 31-030), or whether the text means what it
shows. See the [preflight guide](../accessibility-preflight.md) for the full
list of cases left `NotChecked`.

veraPDF 1.30.3 differs on two cases, both measured on synthetic files without
font programs. It fails unembedded Symbol and ZapfDingbats fonts without an
`/Encoding`, which the native rule maps through their built-in encodings. For
fonts with MacExpertEncoding it reports rules 7.21.7-2 and 7.21.8-1, while the
native rule passes their codes as Matterhorn 31-027 allows. See the
[veraPDF test cases](../accessibility-verapdf.md#validation).

## Upgrading from 7.15.0

The tool requires .NET 10. When your NuGet source lists 7.16.0, update an
existing global installation with this command.

```sh
dotnet tool update --global io7.FreePDF.Accessibility.Tool --version 7.16.0
```

If your application uses the FreePDF libraries, update its FreePDF packages
together and rebuild for assembly version `7.16.0.0`. The public API is
unchanged. Reports list the new rule, and `RulesetVersion` is `1.2.0`.

## Validation

All 7.15.0 release gates apply, plus:

- 1,485 regression tests in all (1,400 in 7.15.0) and 72 accessibility tool
  tests (70 in 7.15.0), with two new hostile inputs for fonts that share one
  `/Differences` array.
- 45 synthetic probe files compared with veraPDF 1.30.3 set the cases of the
  rule. Six adapter fixtures run both validators in CI: mapped, missing,
  custom encoding, forbidden value, and a glyph name in and outside the lists.
- Reviews before release found and fixed six defects. One was a cache limit
  that read a ToUnicode map again for every string after 256 fonts. Another was
  a damaged map stream that ended the whole scan. A third let a named encoding
  pass codes of a map the check could not read. The others treated null
  entries as present, copied whole glyph names into findings, and walked a
  shared `/Differences` array once per font. Two of the reviews were static
  reviews by OpenAI Codex (gpt-6-astra).
