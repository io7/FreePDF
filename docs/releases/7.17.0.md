# FreePDF 7.17.0

FreePDF 7.17.0 checks that the text of a PDF selects real glyphs. PDF/UA-1
forbids references to the `.notdef` glyph (ISO 14289-1 7.21.8), and visible
text must select glyphs that the embedded font program contains (7.21.4.1).
Both `PdfAccessibilityScanner.Scan` and the `freepdf-a11y` tool run the check
as rule `FPDF-A11Y-GLYPH`.

## What the glyph check reports

The check reads the same codes as the Unicode check of 7.16.0: every code that
`Tj`, `TJ`, `'` and `"` show on pages and in invoked forms, with the active
font.

A code fails in every rendering mode when it selects `.notdef`:

- a `/Differences` name `.notdef`;
- a code that the encoding of a Type 1 or Type1C font does not name;
- glyph 0 of a TrueType CIDFont after its `CIDToGIDMap`;
- CID 0 of a CID-keyed CFF font.

Visible text also fails when it selects a glyph that the embedded program does
not contain:

- a glyph index past the program, or a CID past a `CIDToGIDMap` stream;
- a CID that the charset of a CID-keyed CFF program does not list;
- a glyph name that the Type 1 `CharStrings` or the CFF charset does not list;
- a Type 3 name without a procedure in `/CharProcs`;
- a simple TrueType code that no cmap or `post` lookup finds.

Each page reports its first `.notdef` and its first missing glyph, with the
code and the path to the font.

The check reads embedded TrueType (`FontFile2`), Type 1 (`FontFile`) and CFF
(`FontFile3` with subtype `Type1C` or `CIDFontType0C`) programs and Type 3
procedures. A Type 1 or Type1C font takes the glyph name from `/Differences`,
else from its named base encoding, else from the built-in encoding of its
program (ISO 32000-1 9.6.6.2). A simple TrueType font uses the lookups of
ISO 32000-1 9.6.6.4. A code that only a WinAnsi or MacRoman base encoding names
has its Annex D glyph name: WinAnsi `80` is `Euro`.

```sh
freepdf-a11y document.pdf --format json --output audit.json
```

## Changed results

- The rule set and the requirements inventory are now version 1.3.0. Matterhorn
  conditions 31-011 and 31-030 name `FPDF-A11Y-GLYPH` as partial native
  coverage.
- A file that passed the checks of 7.16.0 can now fail. For example, XeTeX
  writes glyph 0 when a font has no glyph for a character, and logs "Missing
  character". Such a PDF now fails the glyph check, as it fails veraPDF.
- Text whose glyphs the check cannot assess is `NotChecked`. A scan without
  failures then ends as `Incomplete` and the CLI exits with `3`. Common causes
  are OpenType programs in `FontFile3`, Type 1 programs in PFB form or without
  eexec encryption, and invisible text, such as an OCR layer, in a font without
  an embedded program.

## Memory and time

Font programs do not count toward `MaxDecodedBytes`. The scan reads each
program once. A program that inflates past 32 MiB, or past 256 MiB for all
programs of a scan, leaves only its own font `NotChecked`. The glyph names and
CID tables kept from all programs of a scan share 1,048,576 entries. A font
whose program does not fit in what is left is `NotChecked` too.

## Known limits

The check does not judge glyph shapes, or whether the text means what it
shows. These give `NotChecked`: OpenType programs in `FontFile3`, CFF2, CFF
font sets, synthetic CFF fonts, the Expert charsets and encodings, built-in
Type 1 encodings in forms other than `StandardEncoding def` or a 256-entry
array set by `dup code /name put`, and damaged programs. See the
[preflight guide](../accessibility-preflight.md) for the full list.

veraPDF 1.30.3 passes three cases that ISO 14289-1 7.21.8 forbids and that the
native rule fails:

- a `CIDToGIDMap` stream that maps the shown CID to glyph 0;
- a code that the built-in encoding of a Type1C program does not name;
- glyph 0 of a CFF program without CIDFont operators, where ISO 32000-1
  9.7.4.2 uses the CID as the glyph index.

See the [veraPDF test cases](../accessibility-verapdf.md#validation).

## Upgrading from 7.16.0

The tool requires .NET 10. When your NuGet source lists 7.17.0, update an
existing global installation with this command.

```sh
dotnet tool update --global io7.FreePDF.Accessibility.Tool --version 7.17.0
```

If your application uses the FreePDF libraries, update its FreePDF packages
together and rebuild for assembly version `7.17.0.0`. The public API is
unchanged. Reports list the new rule, and `RulesetVersion` is `1.3.0`.

## Validation

All 7.16.0 release gates apply, plus:

- 1,641 regression tests in all (1,485 in 7.16.0) and 75 accessibility tool
  tests (72 in 7.16.0). The three new tool tests are hostile inputs: 3,000
  fonts with CID-keyed CFF programs of 65,534 glyphs each, a TrueType `post`
  table with 15 million strings, and one 1 MiB CFF glyph name that 65,534
  glyphs share. Each ran out of memory under the 256 MiB heap limit before the
  bounds above.
- Seven adapter fixtures run both validators in CI: TrueType glyph 0, a glyph
  past the program, a `CIDToGIDMap` to glyph 0, a Type 1 name that the program
  lacks, a Type1C code that WinAnsiEncoding does not name, a CID that a CFF
  charset lacks, and a Type1C built-in encoding that does not name the code.
- Local probes with the URW base-35 fonts as Type 1 and Type1C programs, and
  PDFs made by pdfTeX, XeTeX and Ghostscript, gave the same pass or fail
  verdicts in both validators, apart from the Type1C built-in encoding case
  above. These fonts and PDFs are not in the repository.
- Four static reviews by OpenAI Codex (gpt-6-astra), two on each pull request,
  found defects that were fixed before release, each with a test that failed
  first. A WinAnsi or MacRoman code never reached the TrueType `post` lookup,
  so a glyph named only there was reported missing. cmap readers ignored
  subtable lengths, so an offset into the next subtable could pass a missing
  glyph. `dup 256 /A put` in a Type 1 encoding ended the whole scan. A CFF name
  that many glyphs share was built again for each glyph.
